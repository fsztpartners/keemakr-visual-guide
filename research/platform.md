# Keemakr v2 platform architecture and latency

## What is the business operator, and what actually exists?

### Takeaway
Keemakr is best taught as a shared business desk that can answer, prepare, obtain permission, and execute work in installed business departments. “Pack” is the implementation name for a reusable business department bundle; “capability” is a named, governed action that bundle offers. The source is a snapshot of origin/v2 on 25 November 2026, SHA b5f3402e71a983cecb12061511eb88714cdd1ba4. This is source inspection, not deployment, security certification, or a performance benchmark.

### Cited Findings
- A scaffold specification includes a department, table shapes, named business actions with input/output schemas, business instruction paths, external app requirements, and optional runtime URL. Customer names and tenant identity are deliberately excluded: the bundle is reusable across organizations. The scaffold schema is narrower than all hand-authored runtime possibilities; do not present its 16-action limit as a universal business limit. [src/lib/packs/spec.ts:1-103](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/packs/spec.ts#L1-L103)
- The worker identity is derived from department; the installing business gives it a personal name. This explains “Sales department” before introducing the configurable agent persona. [src/lib/packs/spec.ts:105-121](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/packs/spec.ts#L105-L121)
- Search chooses candidate actions using semantic meaning and lexical matching, then hydrates enabled/readiness state; discovery itself grants no authority. Embeddings are best effort, lexical fallback remains available. The clear-match threshold is explicitly described as not calibrated. [src/lib/marketplace/capability-search.ts:1-57](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/marketplace/capability-search.ts#L1-L57)
- Governed action execution has an explicit sequence: resolve exact installed contract, check installation and dependency readiness, validate input, persist operation identity, possibly wait for approval, mint a grant reduced to the action's declared dependencies, call runtime, validate output and settle. Agent, team lead, and TypeScript targets can answer. [src/lib/marketplace/capability-invoke.ts:1-36](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/marketplace/capability-invoke.ts#L1-L36)
- The public signed-in invoke route uses the authenticated session organization and member, validates action key, and returns 202 for pending approval. The file still describes the Operator caller as interim until Task Operator exists. This is an actual integration seam, not proof that the whole task architecture is absent. [src/app/api/capabilities/[slug]/[key]/invoke/route.ts:1-89](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/app/api/capabilities/[slug]/[key]/invoke/route.ts#L1-L89)
- A separate older Work/ability lane remains: operation/flexible/fixed execution kinds, prepare/exact-action review, explicit work records and status. The operator's pack-operation tool says use this only if capability search finds no suitable action. Teach the governed action lane first, then explain the compatibility lane to senior developers. [agent/tools/pack-operation.ts:5-30](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/agent/tools/pack-operation.ts#L5-L30) [src/lib/work/abilities.ts:17-120](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/work/abilities.ts#L17-L120)
- Ordinary Work operations re-check live membership, installed runtime, invocation permission and role; input is validated; a prepared exact action must match the declared preparation relationship and action digest. Preparing is neither running nor requesting review. [src/lib/work/operations.ts:20-143](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/work/operations.ts#L20-L143)
- Chat has materially diverged from older domain prose: current agent configuration says Core keeps no copy of chat and reads replay Eve's session log. A live comment says old conversation_turns hop columns are no longer written. Do not draw the historical durable Core turn/run graph as current chat storage without qualification. [agent/agent.ts:4-28](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/agent/agent.ts#L4-L28) [src/lib/operator/turn-hops.ts:1-49](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/operator/turn-hops.ts#L1-L49)
- Starting a conversation creates an Eve session, registers the session in Core before sending, then waits for receipt/projection. Existing-chat sends can use client event sequence to avoid a full snapshot response. Approval notes and attachment preparation overlap in current code. [src/lib/operator/eve-conversation.ts:240-301](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/operator/eve-conversation.ts#L240-L301)
- The Company Brain has a common revisioned-store abstraction and runtime-selectable substrates: Mesa, the HTTP Knowledge Store, or explicit Postgres; actual deployment choice is unknown from source alone. [src/lib/brain/store.ts:96-130](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/brain/store.ts#L96-L130)

### Inferences
- A useful diagram has five layers: people and channels → Kee conversation → server permissions/approval → installed business department runtime → company records, business instructions and external apps. AI proposes the next step; the server decides what may execute. This is a teaching synthesis of the contracts above, not a deployment topology claim.
- “Runs a business” needs a precise promise: it completes named business workflows under configured permissions, connections, policies and human decisions. It is not a claim that every clinic process, marketing activity or business decision is automated.
- Avoid treating marketing and clinical data as one shared free-text pool. Specific business identity, purpose and audience remain important even where both departments belong to one organization.

### Gaps
- No production environment, live installation list, deployed SHA, provider contract, data residency configuration, patient data, or production trace was read. Code present does not establish that a customer can use it today.
- No claim of HIPAA/PHIPA compliance follows from architecture alone; the separate domain researcher should verify legal requirements and distinguish technical controls from vendor contracts and operational evidence.

## How are authority, channels and background work controlled?

### Takeaway
The system separates the reusable business code from each organization's permission to use it. A short-lived signed grant is a scoped entry pass, not the business data itself. Background work and customer messages have their own identities and retry rules.

### Cited Findings
- The capability guard derives tenant from the verified grant, binds the audience to the installed runtime resolved server-side, checks scopes and limits, and represents the human acted for separately from scopes. It explicitly warns that a human identity never expands permission. [src/lib/capability/server.ts:1-55](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/capability/server.ts#L1-L55)
- Tenant transactions set the restricted app_tenant role and tenant identifier transaction-locally; explicit tenant predicates remain the primary control. Outside the helper the owner connection bypasses RLS. Nested transactions or module-level SQL inside its callback can bypass isolation and exhaust the pool. [src/lib/db.ts:329-359](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/db.ts#L329-L359)
- Rate limit subjects vary by lane: member, customer conversation, patient link, event delivery. The comments record prior failure patterns where tenant-wide buckets let one open screen or several patients starve the whole organization. These are historical rationale in code, not a current reproducible defect claim. [src/lib/capability/server.ts:161-205](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/capability/server.ts#L161-L205)
- Customer messaging dispatch checks conversation ownership, owner epoch and applicable sending window immediately before waking the business agent; channel replies re-check ownership again. It serializes one turn per conversation, has a 20-second delivery-attempt timeout, a 60-second lease, eight attempts, and retry spacing starting at 15 seconds capped at 15 minutes. [src/lib/channels/dispatch.ts:1-84](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/channels/dispatch.ts#L1-L84)
- External voice calls use LiveKit: browser microphone or SIP phone caller joins a room, Core asks the installed business runtime to join, and the voice agent owns the model connection. Audio does not pass through Core in this lane. Startup calls are bounded at 10 seconds, with a 202 acknowledgement allowing the agent to join afterwards. [src/lib/voice/calls.ts:1-54](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/voice/calls.ts#L1-L54)
- A phone call does not inherit proof merely because caller ID matches a previously verified text conversation. Its grant must record proof obtained on that call before it receives verified treatment. Human takeover or closing the conversation ends the call's ability to act. [src/lib/voice/call-chat.ts:92-122](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/voice/call-chat.ts#L92-L122)
- Events are durable queued deliveries. Grants bind event, delivery attempt, handler, content digest, subscription and deployment. Event worker permits at most five in-flight attempts per runtime within one sweep, explicitly not a service-wide quota. [src/lib/events/worker.ts:20-25](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/events/worker.ts#L20-L25)
- Event delivery allows ten transient attempts; 30-second attempts have 60-second leases; exponential backoff starts around one minute with deterministic plus/minus 25% spreading and caps at one hour. [src/lib/events/delivery.ts:292-296](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/events/delivery.ts#L292-L296) Lease expiry is recovery, explicitly not exactly-once execution. [src/lib/events/delivery.ts:6-15](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/events/delivery.ts#L6-L15)
- Event publication can trigger an after-response 20-second wake; a once-per-minute sweep catches misses. Therefore normal event delivery need not always wait for cron, but fallback latency remains important. [src/lib/events/wake.ts:1-26](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/events/wake.ts#L1-L26)
- Scheduler source describes one-minute cron and four lanes: reconciliation, machine claims, follower recovery, due checks. Each receives bounded slices; the whole tick stops admitting work at 45 seconds and preserves fairness position. Network calls do not run inside its transactions. [src/lib/scheduler/tick.ts:1-50](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/scheduler/tick.ts#L1-L50)
- Work terminal states include uncertain alongside completed, rejected, cancelled and failed. An uncertain external effect is therefore a product state worth explaining, not something to flatten into “failed, retry.” [src/lib/work/state.ts:1-5](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/work/state.ts#L1-L5)

### Inferences
- Teach safe retry with an appointment example: request accepted but connection lost does not prove booking failed. Reconcile by operation identity or provider receipt before asking the provider to book again.
- Event delivery ordering can introduce head-of-line blocking within the chosen binding boundary; comment at delivery.ts:116 says one live lease per binding also serializes unrelated subjects. Before widening concurrency, determine what ordering the domain actually needs and preserve idempotency.
- An approval diagram must show separate moments: draft prepared → review requested → reviewer sees exact action → decision recorded → gates checked again → action executed → outcome verified. Waiting on a person can last days and is not model latency.

### Gaps
- Presence of lease/idempotency mechanisms does not establish exactly-once effects across every external provider. Each provider write must be audited independently.
- Unit/integration test files were inspected as coverage evidence only and were not executed. Examples include concurrent lease claims and disabled-pack behavior in tests/events/claim.itest.ts:188-316; timeout scaling and non-retry of ambiguous runtime timeouts in tests/marketplace/capability-timeout.test.ts:25-321.

## Where does latency come from, and what should the team do?

### Takeaway
Measure time to receipt, first meaningful text, completed business effect, and time waiting for a person separately. The system already contains focused improvements: discovery caching, turn-hop logs, provider routing and compaction, warm-function grouping, immediate event wake, and action-specific time budgets. Proposed fixes below are hypotheses to validate, not measured savings.

### Cited Findings
- Core turn-hop logging splits request prechecks/queue, pre-send work, Eve acceptance and response replay; Eve logging splits first step, first model output, first nonblank visible text, and stop. Both share session tail and turn ID. Steering or answering an existing turn requires careful joining because its clock started earlier. [src/lib/operator/turn-hops.ts:1-49](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/operator/turn-hops.ts#L1-L49) [agent/hooks/turn-hops.ts:36-83](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/agent/hooks/turn-hops.ts#L36-L83)
- The database module logs per-instance connection queue maxima, busy connections, event-loop delay p99 and max over 15-second windows when meaningful waiting occurs; idle suspension is filtered from the loop histogram. Pool checkout defaults to 30 seconds; per-statement timeout defaults off. These are code defaults, not measured production p99 values. [src/lib/db.ts:9-47](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/db.ts#L9-L47)
- Ability discovery caches a Promise for one minute keyed by tenant, installation, version and runtime. Concurrent callers share discovery; failures are generally evicted, while a missing route remains cached for the minute. Source comments say repeated discovery round trips previously cost seconds. Live membership/access checks remain outside the descriptor cache. Current concierge configuration is a low-reasoning, auto-cached Anthropic route; drafting has reasoning off. Historical probe timings appear in comments, but are not independently reproduced and should not be reported as present benchmarks. ### Inferences
#### Six latency stories for the guide (illustrative, no measured values)
1. **Fresh typed question.** Browser → authentication/ownership → screen context → optional new session/attachment processing → Eve acceptance → model reasoning → discovery → governed action → records/provider → model explanation → streamed words. Draw serial arrows for dependent work and parallel branches only where source supports it. The first investigation is which span dominates, not “switch models.”
2. **Long ongoing chat.** Bigger retained history adds input work and tool-result processing. Check actual token counts, cache hit rate and model step count. Compare bounded history/compaction against a fixed fact-recall evaluation before deploying changes.
3. **Sales batch enrichment.** N items each call external search, lookup and crawl. T_serial is approximately sum of stage times over items; T_parallel is bounded by the slowest critical path plus batching/queue overhead. Bounded concurrency can help independent items, but quotas, provider limits, duplicate suppression and per-item partial outcomes matter. Move a large batch to tracked asynchronous work with receipts and checkpoints when it exceeds interactive budgets.
4. **Member live voice.** Speech-end detection → voice model determines tool call → ask_kee travels through typed Operator work → voice model speaks answer. A “let me check” masks silence but does not shorten completion. Evaluate a safe, read-only snapshot or direct deterministic read for frequent questions; quick answers are a proposed V2 port, not active current behavior. Preserve exact names and numbers and do not route risky writes around the governed action path.
5. **Patient voice.** Audio room join → Pack agent join → speech model → governed domain reads/writes/proof → spoken response. Separate room startup from response after each utterance. Identity proof and staff takeover are necessary controls, not “unnecessary latency.” Measure without patient text/audio in general telemetry.
6. **Scheduled/event work.** Time due → wake/sweep → lease/queue → runtime startup → provider work → report/settlement. Include scheduler lateness, retry count and age of oldest ready item; model speed alone cannot fix a missed sweep or head-of-line blocking.

#### Proposed measurement plan and acceptance criteria
- Phase 0: inventory installed/deployed versions, current runtime/DB/model regions and provider contracts; build one diagram per voice lane; record which knobs are live. Acceptance: every topology arrow has a source owner and a deployment verification status.
- Phase 1: instrument browser submit-to-receipt, first meaningful text/audio, Core hop spans, model step/input/output counts, dependency-read time, Pack round trip, provider result and business completion. Correlate by stable operation IDs and trace context. Acceptance: synthetic requests can be followed end to end without raw sensitive content.
- Phase 2: establish a reproducible baseline for cold/warm chat, long context, one vs ten sales items, failed providers, interrupted approval, patient proof, staff takeover, event bursts and scheduler backlog. Report sample count, environment, p50/p95/p99 and failures separately. Acceptance: another developer can rerun the workload and explain each large tail.
- Phase 3: improve the dominant measured bottleneck one change at a time: parallelize independent reads, reduce repeated discovery/context, optimize deterministic reads, tune bounded batch concurrency, checkpoint long work, and use provider routing supported by actual evaluation. Acceptance: latency improves on the target scenario while task correctness, isolation, refusal and duplicate-effect tests remain at least as strong.
- Phase 4: define product-specific SLOs for first acknowledgement, first useful answer, booking completion, scheduled lateness and recovery. Keep human wait out of machine SLOs. Acceptance: dashboard/alerts identify symptoms and owner; rollback threshold and runbook are explicit.
- Phase 5: use load and fault tests to validate burst fairness, lease expiry, duplicate callback, ambiguous timeout, provider rate limiting, cancelled work and model fallbacks. Acceptance: no duplicate booking/send in the synthetic workload; unresolved outcome is surfaced honestly; another tenant still progresses.

#### Plain-language glossary and teaching guidance
- Pack → **business department bundle**: reusable code, screens, records, rules and actions for a job area. Keep “pack” as a small engineering label.
- Capability → **named business action**: e.g. find suitable appointments; has an agreed input/output contract and permission rules.
- Ability → **older Work operation**: compatibility vocabulary whose operation/flexible/fixed execution differs from the capability contract lane.
- Handler → **event responder**: code called when a named event arrives.
- Grant → **temporary scoped entry pass**: signed authority for one runtime/lane, company, purpose and time.
- Runtime → **where department code executes**: can be a separately deployed service; not the user's browser.
- Closure → **the exact dependencies this action needs**: not every tool the whole bundle owns.
- Brain → **versioned company instructions and facts**: not the model's private memory and not automatically the patient record system.
- Table → **structured business ledger**: schema-bound rows; readers must know which source is authoritative.
- Event → **a recorded fact another process reacts to**: “appointment requested,” not an instruction to execute arbitrary text.
- Receipt → **confirmation a request was accepted**: not proof its business effect completed.
- Uncertain → **outcome needs reconciliation**: neither confirmed success nor proof of failure.

### Gaps
- No real latency distribution is available. All scenario formulas and acceptance criteria are proposals. Existing constants and historical code comments are not benchmarks.
- There is no evidence here that the new member voice API is integrated and deployed in every desktop/mobile/web client, nor that all organizations are enabled.
- Performance recommendations follow the primary OpenAI latency guidance (reduce model work/output, reduce sequential requests, parallelize independent work, stream useful progress), and OpenTelemetry's model of correlated distributed spans. Keep these as general engineering principles, not a guarantee of savings: [OpenAI latency optimization](https://developers.openai.com/api/docs/guides/latency-optimization), [OpenTelemetry traces](https://opentelemetry.io/docs/concepts/signals/traces/). PostgreSQL's lock documentation explains why transaction/row lock waits must be measured distinctly: [PostgreSQL explicit locking](https://www.postgresql.org/docs/current/explicit-locking.html).


### User priorities and verified chat orchestration supplement
The user has now chosen a mixed team audience, everyday words with exact engineering terms beside them, US clinics/HIPAA first, and reliable outcomes/permissions before chat and tool speed. Keep voice as a secondary comparison. The roadmap order should therefore be: prove correct authorized effect and honest outcomes → measure real chat/tool critical paths → optimize without weakening those guarantees.

**Actual typed-chat sequence, without invented fixed hop counts:**
1. Client submits a message. Core verifies ownership/authentication and rate limit, resolves open-screen/explanation/spoken context, then calls sendTurn. Each of these can contain database reads; the browser-network and render times are outside the server hop timers. [src/app/api/operator/conversations/[id]/turns/route.ts:19-65](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/app/api/operator/conversations/[id]/turns/route.ts#L19-L65)
2. Eve session attachment uses the client's last sequence when supplied. Attachment preparation and approval-note retrieval overlap. Core waits for message receipt. On normal stream-following messages it can return the stream receipt; otherwise it replays and folds the log into a projection. [src/lib/operator/eve-conversation.ts:277-300](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/src/lib/operator/eve-conversation.ts#L277-L300)
3. The model's business-action path uses capability-search. That is a direct tool which resolves installed departments, semantic/lexical matches and member-visible readiness. Description tells it to stop repeated searches, because repeated search/read loops previously lasted minutes. [agent/tools/capability-search.ts:23-81](https://github.com/fsztpartners/keemakr/blob/b5f3402e71a983cecb12061511eb88714cdd1ba4/agent/tools/capability-search.ts#L23-L81)
4. After the selected contract, the model calls capability-invoke, a durable workflow tool.
