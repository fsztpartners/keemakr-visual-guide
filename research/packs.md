# ClinicOS and Sales packs actual behavior

## What do these business departments contain and own?

### Takeaway
ClinicOS is a substantial clinic front desk and operations implementation; Sales is an aesthetic-practice outbound pipeline with a restricted inbound conversation agent. Neither folder, a manifest declaration, nor test presence proves a tenant is live, configured, safe, or compliant. Research snapshot: 25 November 2026. ### Inferences
- Teach **business work first**: “receive enquiry → understand request → verify person → offer times → confirm booking → prepare visit → hand over to clinician → follow up”, then attach the technical layers. For Sales: “find practices → gather evidence → qualify → review → enroll → observe replies”.
- A pack is more than prompts and more than a UI plugin: the visible evidence includes action contracts, real code, schemas, agent instructions, dependency requests, events and recurring work. Installation needs tenant setup and policy bindings.
- ClinicOS is much broader than the older Sales pack; capability counts do not measure quality or production readiness.

### Gaps
- Tenant installations, grants approved, connection credentials, actual channel binding IDs, live UI parity and deployed SHAs were not inspected. `runtime.status: declared` and a URL are configuration claims, not a deployment health test.
- The detached Core v2 reference is separately researched by the platform agent. Sales uses old `@keemakr/*` prerelease caret pins; ClinicOS pins named v2 snapshots (package.json). Compatibility needs an actual install/contract smoke run, not confidence based on matching field names.

## How do chat, tools and the business journeys actually run?

### Takeaway
ClinicOS patient conversations can perform constrained direct booking work under channel grants; staff requests use named action previews/approvals. Sales chat starts a tracked multi-step task, while its external conversation agent only responds or hands over. These are different action lanes and must not be flattened into “the agent runs everything”.

### Cited Findings
- ClinicOS **staff action lane**: Core selects an action and mints a scoped grant → POST pack `/capabilities/[key]/invoke` → SDK verifies authority and dispatches named binding → implementation calls back to Core for tenant Tables/Medplum → returns success/failure envelope. The route refuses missing runtime authority with 503. SDK verification is delegated, not independently audited here. [Invoke route, lines 1–55](/Users/sobingt/projects/covalify/clinicos/app/capabilities/[key]/invoke/route.ts:1).
- ClinicOS **patient chat lane**: Core delivers turn to pack `/channels/v1/deliver`; pack forwards body and bearer to configured Concierge/Intake Eve app; downstream app verifies turn grant. One extra network hop exists. Unknown handler gets non-retryable 404. Forward fetch deadline is 55 s, host maxDuration 60 s. [Forwarder, lines 1–38](/Users/sobingt/projects/covalify/clinicos/app/channels/v1/deliver/route.ts:1).
- Concierge handler does not read Core before dispatching into Eve session, because Core's channel attempt is described as 20 s. First session step screens safety before main model wakes, and adds person context separately from user words. Core ownership-change deliveries include messages missed while staff held the conversation. [Inbound path, lines 1–12,47–90](/Users/sobingt/projects/covalify/clinicos/agents/concierge/agent/channels/inbound.ts:1). The 20 s statement is a code comment and requires Core confirmation by the platform researcher.
- Main Concierge model uses Core's dynamic `concierge` resolver and `defaultTools:false`; it has declared tools rather than unrestricted shell/files/web. [Agent, lines 1–12](/Users/sobingt/projects/covalify/clinicos/agents/concierge/agent/agent.ts:1).
- Clinic configuration loads settings, Brain version, known person and first Brain read in parallel; per-turn session cache reuses the view; unchanged Brain stamp reuses Brain content across turns. It still re-reads version/settings/person as appropriate, so “cached” does not mean zero callbacks. Brain file groups are parallelized too. Failed Brain read can retain previous session files without a version stamp, causing retry next turn. [readClinic, lines 76–117](/Users/sobingt/projects/covalify/clinicos/agents/concierge/agent/lib/clinic.ts:76).
- Synthetic example **Alex wants a consultation**: Concierge answers from clinic reference, handles identity, records enquiry interest/reason, offers actual Medplum times, reads back one exact choice, waits for clear yes, then invokes its constrained book tool. The tool checks fresh safety holds, contact/access, current readback, latest staff interference, whether words actually reached the person, and evidence of identity; another person's booking is handed to staff. [Patient book tool, lines 29–80](/Users/sobingt/projects/covalify/clinicos/agents/concierge/agent/tools/book.ts:29).

### Inferences
- Teach “three lanes” visually: **conversation**, **governed named action**, **tracked background task**. Then show event handlers as reactions after a committed business fact. ClinicOS patient booking is a controlled tool within conversation, staff booking is a named approved action, and Sales sourcing is a background task.
- Perceived chat latency includes every pre-model safety/config/person read, the model's first output/tool choice, each tool/provider callback and final reply. A model TTFT alone does not capture this experience.
- Patient confirmation can be acknowledged when Medplum outcome is proven while downstream operational bookkeeping continues (booking has an onBooked hook). Design must still show failures in confirmations/intake/events separately from whether the visit exists.

### Gaps
- No end-to-end live synthetic journey was executed; sources show the design and handlers, not currently operating tenants.
- Screens and actions are implemented; whether they match live schemas is unverified. ClinicOS even provides check:live-columns, but running it against a tenant is outside this read-only research.

## What are the gaps, delay mechanisms, failure boundaries and HIPAA evidence?

### Takeaway
Most meaningful risks live at boundaries: provider outcome vs local record, tenant policy vs pack expectation, channel identity vs chart identity, and operational data vs privacy claims. Latency remediation must preserve those checks and outcome truth. There are no measured latency distributions in this research.
